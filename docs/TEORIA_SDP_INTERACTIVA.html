¿Qué es Databricks? Base

Databricks es una plataforma de datos e inteligencia artificial en la nube. En un solo lugar puedes guardar datos, transformarlos, analizarlos con SQL, programar procesos automáticos y entrenar modelos de machine learning. La crearon los mismos autores de Apache Spark.

AnalogíaPiensa en Databricks como una cocina industrial: los datos son los ingredientes, Spark es el equipo de cocineros que trabajan en paralelo, Delta Lake es la despensa ordenada y Unity Catalog es el inventario con control de quién puede tomar qué.

Piezas principales

⚡

Apache Spark

Motor que procesa datos en paralelo repartiendo el trabajo entre muchas máquinas. Así procesa millones de filas rápido.

🔺

Delta Lake

Formato de tabla sobre archivos Parquet. Agrega transacciones ACID, historial de versiones (time travel) y validación de esquema.

🗂️

Unity Catalog

Gobierno de datos: organiza todo en catálogo.esquema.tabla y controla permisos, linaje y auditoría.

🖥️

Compute

Clusters, SQL Warehouses y Serverless (Databricks administra las máquinas por ti). En el taller usamos serverless.

📓

Notebooks y Jobs

Notebooks para escribir código (Python, SQL). Jobs para programar ejecuciones automáticas.

🔁

Lakeflow SDP

Pipelines declarativos: describes las tablas y Databricks se encarga de orquestar, reintentar y validar.

¿Para qué es útil Databricks?

Ya con las capas Bronze, Silver y Gold claras, veamos qué equipos usan los datos y en qué capa trabajan. Todos usan las mismas tablas gobernadas, sin copiarlas a otros sistemas.

Bronze → Silver → Gold

Construir pipelines que llevan datos desde sistemas origen (por ejemplo AS400, bases de datos, archivos) hasta tablas limpias y confiables, en batch o casi en tiempo real. Esto es lo que hacemos en el taller.

Gold

Consultar las tablas Gold con SQL, crear dashboards y dar a negocio KPIs como “monto total transaccionado por mes”.

Silver y Gold

Entrenar modelos (por ejemplo, riesgo de crédito o detección de fraude) usando las mismas tablas, con MLflow para rastrear experimentos.

Todas las capas

Saber quién accede a qué dato, de dónde viene cada tabla (linaje) y aplicar permisos por catálogo, esquema o columna con Unity Catalog.

Data Vault Modelado Silver

Data Vault es una forma de modelar datos pensada para guardar toda la historia, integrar muchos sistemas origen y crecer sin rehacer el modelo. Separa cada concepto de negocio en tres tipos de tabla: Hubs, Satélites y Links.

🔵

Hub = la identidad

Guarda solo la llave de negocio (por ejemplo, el código del cliente) una vez, sin duplicados. Responde: “¿qué clientes existen?”

🟡

Satélite = la descripción

Guarda los atributos que describen al hub (nombre, ciudad, estado) y cómo cambian en el tiempo. Responde: “¿cómo es este cliente?”

🟢

Link = la relación

Une dos o más hubs. Responde: “¿qué cliente tiene qué préstamo?”

Analogía: una cédula de identidadEl Hub es el número de cédula (nunca cambia). El Satélite es la información de la persona: dirección, estado civil, teléfono (cambia con el tiempo y queremos el historial). El Link es, por ejemplo, el contrato que une a esa persona con un préstamo.

¿Por qué usar un hash (SHA-256) como llave?

En cada hub calculamos sha2(customer_id, 256), que convierte la llave de negocio en un texto de 64 caracteres. Ventajas:

Siempre igual

La misma entrada produce siempre el mismo hash, sin importar cuándo ni dónde se calcule.

Carga en paralelo

Hubs, satélites y links pueden calcular la llave por separado, sin esperar a que otra tabla genere un ID.

Joins uniformes

Todas las llaves tienen el mismo tipo y largo, lo que simplifica las uniones entre tablas.

Ventajas y cuidados

✅ Ventajas

• Historial completo y auditable.
• Agregar un sistema origen nuevo = agregar satélites, sin romper lo existente.
• Cargas en paralelo gracias al hash.
• Cada tabla tiene una sola responsabilidad.

⚠️ Cuidados

• Hay más tablas que en un modelo tradicional.
• Para consultar hay que hacer varios joins; por eso existe la capa Gold, que entrega datos ya agregados.
• Requiere disciplina en nombres y llaves.

❓ El banco agrega un nuevo campo “segmento del cliente” desde otro sistema. ¿Dónde lo guardarías?

Streaming Procesamiento incremental

Streaming significa procesar los datos a medida que llegan, en lugar de esperar y procesar todo de una vez. En Databricks se hace con Spark Structured Streaming, que trata una tabla o carpeta como una fuente que va creciendo.

📦 Batch

Lee todos los datos cada vez que se ejecuta. Simple, pero si la tabla tiene 100 millones de filas y llegaron 1,000 nuevas, igual procesa las 100 millones.

spark.read.table("raw_data.bronze.trans")

🌊 Streaming

Lee solo lo nuevo desde la última ejecución. Recuerda hasta dónde llegó gracias al checkpoint.

spark.readStream.table("raw_data.bronze.trans")

Conceptos clave

Micro-batch
Spark no procesa fila por fila: agrupa lo que llegó en pequeños lotes (micro-batches) y los procesa uno tras otro. Por eso hablamos de near real time (casi tiempo real): segundos o minutos de latencia.
Checkpoint
Es una carpeta donde Spark guarda hasta qué punto ya leyó (el “offset”). Si el proceso se cae y se reinicia, continúa desde ahí sin perder ni duplicar datos. En SDP el checkpoint se administra automáticamente: no tienes que configurarlo.
Exactly-once (exactamente una vez)
Gracias al checkpoint y a las transacciones de Delta Lake, cada registro de la fuente se escribe una sola vez en el destino, aunque haya fallas.
Fuente append-only
Streaming funciona mejor cuando la fuente solo agrega filas. Si en la fuente se actualizan o borran filas, el stream puede fallar. Para ese caso existen herramientas como create_auto_cdc_flow (sección 8).
Trigger: ¿cada cuánto se ejecuta?
Continuo: el proceso queda corriendo y toma datos apenas llegan.
Disparado (triggered): se ejecuta, procesa todo lo pendiente y se detiene. Se puede programar con un Job (por ejemplo, cada 2 minutos). Nuestro pipeline NRT usa este modo.

Auto Loader Ingesta de archivos

Auto Loader es la forma de Databricks de leer archivos nuevos que llegan a una carpeta (CSV, JSON, Parquet, etc.) de manera incremental. Es streaming aplicado a archivos: detecta cuáles son nuevos y solo procesa esos.

¿Dónde encaja?Normalmente se usa para cargar la capa Bronze: un sistema origen (por ejemplo, una extracción de AS400) deja archivos en un Volume de Unity Catalog y Auto Loader los convierte en una tabla Delta. En el taller generamos Bronze con un notebook, pero en producción lo común es Auto Loader.

Cómo se escribe

from pyspark import pipelines as dp

@dp.table(name="raw_data.bronze.trans_autoloader")
def trans_autoloader():
    return (
        spark.readStream
            .format("cloudFiles")                  # cloudFiles = Auto Loader
            .option("cloudFiles.format", "json")   # formato de los archivos
            .load("/Volumes/raw_data/bronze/landing/trans/")  # carpeta a vigilar
    )

Características importantes

📁 Detecta archivos nuevos

Lleva registro de los archivos ya procesados. Tiene dos modos: directory listing (revisa la carpeta) y file notification (recibe avisos de la nube; útil con muchísimos archivos).

🧬 Infiere el esquema

Lee una muestra de archivos y deduce columnas y tipos. No tienes que escribir el esquema a mano.

➕ Evolución de esquema

Si llega un archivo con una columna nueva, Auto Loader la detecta y la agrega (comportamiento por defecto: addNewColumns, que reinicia el stream una vez para incluirla).

🛟 Datos rescatados

Los valores que no calzan con el esquema se guardan en la columna _rescued_data en lugar de perderse.

Teoría de SDP Lakeflow Spark Declarative Pipelines

SDP es un framework para construir pipelines de datos de forma declarativa: tú describes qué tablas quieres y de dónde salen; Databricks decide cómo ejecutarlas, en qué orden, con qué infraestructura y cómo recuperarse de errores.

Imperativo vs Declarativo

Tú controlas cada paso: leer, transformar, escribir, decidir el orden y manejar errores.

# 1. Leer
df = spark.read.table("raw_data.bronze.cumst")
# 2. Transformar
hub = df.select(F.sha2("customer_id", 256).alias("customer_hk"), ...)
# 3. Validar a mano
if hub.filter("customer_bk IS NULL").count() > 0: raise Exception("nulos")
# 4. Escribir
hub.write.mode("overwrite").saveAsTable("data_vault.plata.hub_clientes_dsh")
# 5. Recordar ejecutar este notebook ANTES que el de satélites...

Declaras la tabla y su regla de calidad. SDP crea la tabla, la escribe, valida y ordena las dependencias.

@dp.materialized_view(name="data_vault.plata.hub_clientes_dsh")
@dp.expect_or_fail("pk_no_nulo", "customer_bk IS NOT NULL")
def hub_clientes_dsh():
    return spark.read.table("raw_data.bronze.cumst").select(...)
ResultadoMenos código, sin escribir .write, sin orden manual, y con métricas de calidad automáticas en la interfaz.

Los 3 tipos de dataset

Streaming Table (ST): tabla Delta que se llena de forma incremental. Cada ejecución procesa solo las filas nuevas de la fuente. Ideal para ingesta y para Silver en near real time.

@dp.table(name="data_vault.plata.nrt_hub_clientes_dsh")
def nrt_hub_clientes_dsh():
    return spark.readStream.table("raw_data.bronze.cumst")  # readStream ⇒ Streaming Table

Úsala cuando: la fuente solo agrega filas y quieres baja latencia o procesar volúmenes grandes sin releer todo.

Materialized View (MV): tabla cuyo resultado siempre refleja la consulta completa sobre la fuente. Databricks la actualiza en cada ejecución (y cuando es posible, la recalcula de forma incremental por ti).

@dp.materialized_view(name="ods.gold.resumen_clientes_dsh")
def resumen_clientes_dsh():
    return spark.read.table("data_vault.plata.sat_clientes_dsh").groupBy("country").count()

Úsala cuando: haces agregaciones (groupBy), joins complejos, o la fuente puede tener actualizaciones/borrados. Por eso Gold siempre es MV, incluso en el pipeline NRT.

Vista temporal: resultado intermedio que no se guarda como tabla. Sirve para reutilizar lógica dentro del pipeline sin publicar nada en el catálogo.

@dp.temporary_view()
def clientes_activos():
    return spark.read.table("raw_data.bronze.cumst").where("status = 'ACTIVE'")

En el taller usamos algo parecido: MVs con private=True en calidad.py. Se calculan dentro del pipeline pero no se publican para los usuarios.

Opciones de ejecución

Dry run (validar sin ejecutar)
Revisa el código, resuelve dependencias y valida que las tablas fuente existan, sin escribir datos. Hazlo siempre antes de la primera ejecución.
Triggered vs Continuous
Triggered: procesa lo pendiente y se apaga (más económico; se programa con Jobs).
Continuous: queda encendido procesando datos apenas llegan (menor latencia, mayor costo).
Development vs Production
Development: pensado para iterar rápido; no reintenta automáticamente ante errores, así ves el fallo de inmediato.
Production: reintenta ante fallas transitorias; es el modo para pipelines programados.
Refresh vs Full refresh
Refresh (normal): las STs procesan solo lo nuevo y las MVs se actualizan.
Full refresh: borra el contenido y checkpoints de las tablas seleccionadas y reprocesa todo desde cero. Úsalo con cuidado: si la fuente ya no tiene datos antiguos, se pierden.
Parámetros del pipeline (configuración)
En Settings → Configuration defines pares llave/valor que el código lee con spark.conf.get(). En el taller así cada ingeniero define su sufijo: 
SUFFIX = spark.conf.get("pipelines.suffix", "dsh")
@dp.materialized_view(name=f"data_vault.plata.hub_prestamos_{SUFFIX}")

Transformaciones y usos de SDP

Dentro de cada función de SDP escribes transformaciones normales de PySpark (o SQL). Estas son las más usadas y cómo aparecen en el taller.

Transformaciones frecuentes

Elegir columnas y renombrarlas. Así creamos las columnas del hub.

spark.read.table("raw_data.bronze.cumst").select(
    F.sha2(F.col("customer_id"), 256).alias("customer_hk"),  # hash de la llave
    F.col("customer_id").alias("customer_bk"),             # llave de negocio
    F.lit("CUMST").alias("record_source"),                # valor fijo
    F.current_timestamp().alias("load_ts"),               # fecha de carga
)

Agregar o reemplazar una columna calculada. En Gold creamos el mes de la transacción:

df.withColumn("transaction_month", F.date_format("travdm", "yyyy-MM"))

Quedarse solo con las filas que cumplen una condición.

df.where("customer_id IS NOT NULL")
df.filter(F.col("traamt") > 0)

Eliminar filas repetidas según una o varias columnas. Clave en hubs (una fila por llave) y links (una fila por par de llaves).

hub.dropDuplicates(["customer_bk"])
link.dropDuplicates(["customer_hk", "deal_hk"])
En streamingdropDuplicates recuerda las llaves ya vistas en el estado del stream. Con volúmenes muy grandes conviene combinarlo con withWatermark para limitar cuánto recuerda.

Combinar dos tablas. Tipos más usados:

TipoDevuelveUso en el taller
innerFilas con coincidencia en ambasCruces normales
leftTodas las de la izquierda + coincidenciasEnriquecer datos

# transacciones cuyo cliente NO existe en cumst (huérfanas)

Agrupar y calcular métricas. La base de la capa Gold.

sat_prestamos.groupBy("currency", "status").agg(
    F.count("*").alias("deal_count"),
    F.sum("principal_balance").alias("principal_balance_total"),
    F.avg("interest_rate").alias("avg_interest_rate"),
)

SDP también acepta archivos .sql. La misma MV de Gold en SQL:

CREATE MATERIALIZED VIEW ods.gold.resumen_prestamos_dsh AS
SELECT currency, status, COUNT(*) AS deal_count, SUM(principal_balance) AS principal_balance_total
FROM data_vault.plata.sat_prestamos_dsh
GROUP BY currency, status;

CREATE OR REFRESH STREAMING TABLE data_vault.plata.nrt_hub_clientes_dsh AS
SELECT sha2(customer_id, 256) AS customer_hk, customer_id AS customer_bk
FROM STREAM(raw_data.bronze.cumst);

Buenas prácticas

1. Un archivo por tipo de tabla
Separa hubs, satélites, links, calidad y Gold. El código es más fácil de leer y revisar.
2. Nombres completos y parametrizados
Usa catálogo.esquema.tabla y lee catálogo, esquema y sufijo con spark.conf.get(). Así el mismo código sirve para cada ingeniero y cada ambiente.
3. Siempre dry run primero
Detecta errores de sintaxis, tablas inexistentes o dependencias circulares sin gastar tiempo ejecutando.
4. No uses acciones dentro de las funciones
Evita .collect(), .count(), .write o display() dentro de un dataset. La función solo debe devolver un DataFrame; SDP se encarga de escribirlo.
5. Elige bien el tipo de expectation
expect para monitorear, expect_or_drop para filtrar filas sucias, expect_or_fail solo para reglas críticas (llaves nulas, integridad).
6. ST para ingesta, MV para agregados
Si la lógica necesita “ver todo” (totales, rankings, joins con tablas que cambian), usa MV.
Resumen en una fraseSDP te deja enfocarte en qué datos necesita el negocio; Databricks se ocupa del orden, la infraestructura, la incrementalidad y la calidad.
